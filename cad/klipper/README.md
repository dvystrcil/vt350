# cad/klipper: the firmware config, checked against the CAD in Kalico batch mode

The firmware is [Kalico](https://github.com/KalicoCrew/kalico) (user, 2026-11-09). The config holds the values the CAD model decides, plus the minimum Kalico needs to load it. Kalico's **batch mode** runs the config and G-code on the host with no hardware (`klippy -i in.gcode -o out.serial -d <dict>`; Kalico `docs/Debugging.md`). The tests here use it to check that the config allows exactly the CAD envelope and refuses anything past it ([#116](https://github.com/dvystrcil/vt350/issues/116)).

| File | What it is |
|---|---|
| `printer.cfg` | The Kalico config's top file: `[printer]` (corexy) and the includes below, in order. `SAVE_CONFIG` writes its block at its end. See [Layout](#layout-294) |
| `mcu.cfg` | The main board, the Octopus Pro H723 |
| `steppers.cfg` | X, Y and three Z steppers, without the limits the CAD decides |
| `cad_values.cfg` | **Generated** by `limits.py --cfg` from the committed CAD logs: X/Y `position_min/max/endstop`, Z `position_max`. Kalico merges them into `steppers.cfg`'s sections. Don't edit by hand |
| `beacon.cfg` | The Beacon (`[beacon]`), its scan mesh (`[bed_mesh]`) and `Z_TILT_ADJUST` by nozzle tap (`[z_tilt]`), #291. **Not included by `printer.cfg` yet**: Kalico batch mode can't load `[beacon]`. `cad/motion/beacon_scan.py` reads it for the start-of-print video. PROPOSED values wait on #291 |
| `t0.cfg`, `t1.cfg` | Tool 0 (Left head) and tool 1 (Right head): the O2S toolboard's `[mcu]`, the extruder, the part fan. `PLACEHOLDER` marks values nobody has decided yet, in every file |
| `pinmap.json` | Generated by `platform/klipper/pinmap.py` (#224): each MCU pin in `printer.cfg` and its includes → a pin on that MCU's simulated board (simulavr atmega644p), for the virtual printer. CI fails when `printer.cfg` uses a pin it doesn't cover |
| `virtual-printer.sh` | The VT350 as a virtual printer (#224): `start` / `status` / `stop`. Passes this folder's values (Kconfig fragments, `printer.cfg`, `pinmap.json`, the save-file seed) to `platform/virtualprinter/virtualprinter.sh`. See [The virtual printer](#the-virtual-printer-224) |
| `xy_mapping.json` | Model → printer XY: origin and axis directions. **Proposed** in [#116](https://github.com/dvystrcil/vt350/issues/116), not confirmed |
| `frontend.cfg` | The web front end: **Fluidd** (owner, 2026-11-10). One include of a vendored client config in `platform/klipper/frontends/`; `python3 platform/klipper/frontend.py --config cad/klipper/frontend.cfg --use mainsail` switches it |
| `toolchanger.cfg` | The tool changer: includes MadMax's macros (`madmax/`, unchanged) and sets the VT350's dock positions and two `[tool]`s. Included by `printer.cfg` |
| `tc_offsets.cfg` | Nozzle offsets (#186): includes MadMax's offset-calibration macros, sets the Mellow MultiHead Zero's pin (an Octopus endstop input, DIAG3), replaces the three macros that would fail on Kalico, and checks the save file before a tool change. Included by `printer.cfg` |
| `madmax/` | MadMax's `toolchanger.cfg`, `toolchanger_macros.cfg`, `tc_offset_calibration_macros.cfg` and `offset_save_file.cfg`, vendored unchanged from `zruncho3d/madmax@277a63c` (GPL-3.0) |
| `dock_params.py` | VT350-specific. Derives every `params_*` in `toolchanger.cfg` from the CAD dock poses and checks the file against them |
| `toolchange.gcode` | Picks up and docks each head: `T0`, `T1`, `UNSELECT_TOOL` |
| `toolchange_timeline.jsonl` | Generated. Every move Kalico planned for `toolchange.gcode`, one JSON line each (the input for #116 AC5) |
| `test_dock_params.py` | `toolchanger.cfg` against the CAD, and the vendored macros against upstream's git blobs. Plain python3 |
| `limits.py` | VT350-specific. Derives each limit from the committed CAD logs, writes `cad_values.cfg` and `envelope.gcode`, and checks the config (`printer.cfg` and its includes) against the logs |
| `envelope.gcode` | Generated. Walks the envelope: the four corners at Z 0 and at the Z floor, then the negative Z `position_min`, then one step past each limit |
| `kalisim/` | The generic core. Runs Kalico batch mode and returns a timeline of planned moves. No FreeCAD, no VT350 knowledge. GPL-3.0 |
| `test_limits.py` | The config against the logs, `cad_values.cfg` against what `limits.py --cfg` writes now, no CAD limit set anywhere else, plus the envelope generator. Plain python3 |
| `test_kalico_batch.py` | Real Kalico, in the container: the pinned commit, one dictionary per MCU, the envelope walk, and the tool changes |

## Layout (#294)

Owner, 2026-11-21: flat, one file per part of the printer, modelled on the owner's Neptune config
([neptune-4pro-klipper-backup](https://github.com/dvystrcil/neptune-4pro-klipper-backup)); every number the CAD model
decides in one generated file. `printer.cfg` includes, in order: `mcu.cfg`, `steppers.cfg`, `cad_values.cfg`,
`t0.cfg`, `t1.cfg`, `frontend.cfg`, `toolchanger.cfg`, `tc_offsets.cfg`. Kalico merges a section that appears in more
than one file (later files win), which is how `cad_values.cfg` fills in `steppers.cfg`'s `[stepper_*]` sections.
Everything that reads the config (`limits.py`, `pinmap.py`, the virtual printer) follows the includes, with
`platform/klipper/pinmap.py`'s loader.

Files come as their part does: `bed.cfg`, `fans.cfg` and `temperature_sensors.cfg` with the bed heater and the
remaining fans (#15); `beacon.cfg` (`[beacon]`, contact homing for Z 0, the scan mesh, `[z_tilt]` by nozzle tap) and
its values in `cad_values.cfg` with #291; `macros.cfg` with the print-start macro; `t2.cfg` … `t4.cfg` when those heads
are wired. The split (#294) changed no setting: the merged sections were identical before and after (53 sections).

## Where each limit comes from

`cad_values.cfg` names the source above every limit (Z `position_min`, not a CAD limit, is in `steppers.cfg` with its
source), and `test_limits.py` recomputes each one from that log:

| Axis | min | max | Source (in `cad/data/logs/`) |
|---|---|---|---|
| X | 4.00 | 346.00 | `sweep_toolhead.log`: "first nozzle X with no new overlap" −416.0 / −74.0, both heads |
| Y | −99.43 | 340.19 | `sweep_toolhead.log`: "nozzle Y reach −68.93 .. 370.69", both heads (lite-78) |
| Z | −15 | 329.43 | min: not a CAD limit (see below); max: `z_sweep.log` `klipper_position_max_configured_mm` |

X and Y are mapped by the proposed `xy_mapping.json`: origin at the print square's front-left corner, model (−420.0, 30.5); X+ = model +X, Y+ = model +Y. With that mapping the CAD gives a 342 × 422.6 mm XY box, so it is **not** the 350 mm square. The nozzle stops 4 mm short of each X edge of the print square and 9.81 mm short of its rear edge (Y 340.19 of 350), while Y below 0 reaches the docks.

**Z `position_min` is the one limit not taken from a CAD log.** Z0 comes from the Beacon nozzle tap (`z_sweep.log`: the nozzle on the magnet sheet) and shifts by fractions of a mm per nozzle. `position_min` only sets how far below Z0 Kalico accepts a command, so per-tool Z offsets and calibration moves aren't refused. −15 matches the AC4 macro source, MadMax `r2pdx_config-v2-Kalico-Beacon` at `zruncho3d/madmax@277a63c` ([vt350#116](https://github.com/dvystrcil/vt350/issues/116)). `limits.py` only requires it to be at or below the CAD floor of 0.

When a CAD log changes, regenerate both files: `python3 cad/klipper/limits.py --cfg > cad/klipper/cad_values.cfg`, then `python3 cad/klipper/limits.py --gcode > cad/klipper/envelope.gcode`, and `python3 cad/klipper/limits.py --check` ("limits: OK"). `test_limits.py` fails while either file is stale.

## The web front end

**Fluidd** (owner, 2026-11-10). Mainsail is the other supported choice. Both are Moonraker clients, and each ships a client config with the same sections (`[virtual_sdcard]` with path `~/printer_data/gcodes`, `[pause_resume]`, `[display_status]`, `[respond]`) and the same `PAUSE` / `RESUME` / `CANCEL_PRINT` macros. Both are vendored unchanged in `platform/klipper/frontends/<name>/client.cfg`, pinned by commit and checked by git blob id. `frontend.cfg` includes exactly one of them. To switch, run:

```sh
python3 platform/klipper/frontend.py --config cad/klipper/frontend.cfg --use mainsail   # or --use fluidd
```

`test_kalico_batch.py` runs the tool changes under each front end and checks that they give the same timeline. On the Pi, the usual install (`ln -sf ~/fluidd-config/fluidd.cfg ~/printer_data/config/fluidd.cfg`, then `[include fluidd.cfg]`) gives the same file. How this repo's config reaches the Pi isn't decided yet.

## The tool changes (#116 AC4)

The macros are MadMax's `r2pdx_config-v2-Kalico-Beacon-2025-07-05` at `zruncho3d/madmax@277a63c` (owner's choice, #116), on `viesturz/klipper-toolchanger@94756df`. Both are GPL-3.0. The kalisim image copies klipper-toolchanger's `toolchanger`, `tool`, `tool_probe` and `tool_probe_endstop` modules into Kalico's `klippy/extras/`. Its `tools_calibrate.py` is left out, so Kalico keeps its own.

MadMax's dock path, with the VT350's values (printer coordinates, PROPOSED mapping):

| Param | VT350 | From |
|---|---|---|
| `[tool T0] params_park_x` / `params_detach_x` | 10.30 / 15.30 | `sweep_toolhead.log` "Left: docked nozzle tip (−409.70, …)"; detach 5 mm (MadMax) away from the keyslot plate, which is on the left head's −X side |
| `[tool T1] params_park_x` / `params_detach_x` | 339.70 / 334.70 | "Right: docked nozzle tip (−80.30, …)"; the mirror image, so detach goes −X |
| `params_attach_y` | −85.96 | docked nozzle Y −49.46 (lite-78: the docks 17 forward, #291), minus the 6.0 mm keyslot slide to the large opening (`sweep_toolhead.log`) |
| `params_close_y` | −63.96 | MadMax's distance from its parked Y (+16), kept |
| `params_safe_shuttle_y` | −43.96 | MadMax's distance (+36). **Unchecked:** set for MadMax's heads; #116 AC5 clash-checks it |
| `params_safe_toolhead_y` | 31.04 | MadMax's distance (+111). **Unchecked**, as above |

Pickup runs `safe_shuttle_y` (at the current X) → `park_x` → `close_y` → `attach_y` (path speed) → `detach_x` (path speed) → `safe_toolhead_y` → back to where the change started. Dropoff runs `detach_x, safe_toolhead_y` → `attach_y` → `park_x` (path speed) → `close_y` (path speed) → `safe_shuttle_y`.

What batch mode shows about the macros on this config:
- **Two unknown commands**, which Kalico reports and skips: `SET_INPUT_SHAPER` (MadMax's `after_change_gcode`; needs an `[input_shaper]`) and `STOP_TOOL_PROBE_CRASH_DETECTION` (MadMax's `dropoff_gcode`; only `[tool_probe_endstop]` registers it, and MadMax's own Beacon config leaves that out too). The test fails if another one appears.
- **The empty carriage goes below Y 0 away from the docks.** It travels at `safe_shuttle_y` (−43.96) along X, and after `UNSELECT_TOOL` it returns diagonally from the dock. Every other move below Y 0 is at a dock's park or detach X.
- **The timeline's `tool` is the active extruder, not what's on the carriage.** klipper-toolchanger switches the extruder before the pickup moves, so the empty carriage's approach to a dock is already labelled with the new tool.
- **No tool detection yet.** MadMax starts by reading a `[gcode_button tool<n>_detect]` per tool. The O2S inputs for that aren't decided, so `toolchanger.cfg` starts with no tool on the carriage, as in the model.

When a dock pose in the CAD changes, run `python3 cad/klipper/dock_params.py --check`. It names every `params_*` that no longer matches. After any change to the config or the macros, regenerate the timeline in the image:

```sh
docker build -q --build-context kconfig=cad/klipper/kconfig -t vt350-kalisim platform/kalisim
docker run --rm -v "$PWD:/repo:ro" vt350-kalisim sh -c 'cd /repo/platform && $KALISIM_PYTHON -m kalisim run \
    --config /repo/cad/klipper/printer.cfg --gcode /repo/cad/klipper/toolchange.gcode \
    --home-file printer_data/config/offset_save_file.cfg=/repo/cad/klipper/madmax/offset_save_file.cfg \
    -d /opt/dicts/octopus-pro-h723.dict -d o2s_left=/opt/dicts/o2s-left.dict -d o2s_right=/opt/dicts/o2s-right.dict' \
    > cad/klipper/toolchange_timeline.jsonl
```

## Running it

```sh
python3 cad/klipper/test_limits.py                 # no Docker: printer.cfg vs the CAD logs
python3 cad/klipper/test_dock_params.py            # no Docker: toolchanger.cfg vs the CAD dock poses
python3 platform/klipper/test_frontend.py          # no Docker: the front-end switch and the vendored client configs
python3 platform/klipper/test_pinmap.py            # no Docker: the pin-map generator and its check
python3 platform/klipper/pinmap.py check --config cad/klipper/printer.cfg --map cad/klipper/pinmap.json   # "pinmap: OK"
python3 cad/klipper/test_virtual_printer.py        # no Docker: a new [heater_bed] fails the virtual printer's drift check
python3 platform/virtualprinter/prepare.py --check --source . --config cad/klipper/printer.cfg \
    --map cad/klipper/pinmap.json --sensors <Kalico's klippy/extras/temperature_sensors.cfg>   # "virtual-printer: check OK"
bash cad/klipper/test_in_container.sh      # Docker: builds the image, runs the Kalico tests; "kalico-batch: OK"
```

The `kalico-batch` workflow runs both on every change to `cad/klipper/` or to the Z sweep log.

To run your own G-code through the config:

```sh
docker build -t vt350-kalisim platform/kalisim
docker run --rm -v "$PWD:/repo:ro" vt350-kalisim sh -c 'cd /repo/cad/klipper && $KALISIM_PYTHON -m kalisim run \
    --config printer.cfg --gcode envelope.gcode -d /opt/dicts/octopus-pro-h723.dict \
    -d o2s_left=/opt/dicts/o2s-left.dict -d o2s_right=/opt/dicts/o2s-right.dict'
```

This prints one JSON line per planned move (`plugins/move_timeline.py`). A move Kalico refuses ends the run.

## The virtual printer (#224)

Batch mode plans moves and exits. The virtual printer keeps Kalico running, live, on simulated boards, with Moonraker
and Fluidd in front, so the macros, fans and config can be clicked through in Fluidd before the hardware exists.

```sh
bash cad/klipper/virtual-printer.sh start    # builds both images, starts, waits: "virtual-printer: ready"
                                             # Fluidd at http://127.0.0.1:8080/ (--port N for another port)
bash cad/klipper/virtual-printer.sh status   # "virtual-printer: ready"
bash cad/klipper/virtual-printer.sh stop     # "virtual-printer: stopped"
```

Each port is its own printer: the container is `virtual-printer` on 8080 and `virtual-printer-<N>` with `--port N`,
so a second one never replaces the first. Give `status` and `stop` the same `--port`.

- **The boards:** each `[mcu]` (the Octopus, `o2s_left`, `o2s_right`) is its own simulavr atmega644p running Kalico's
  AVR firmware, built at the kalisim image's Kalico commit. `pinmap.json` moves every pin onto that board; the config
  copy the container runs (`config/src/cad/klipper/printer.cfg` in Fluidd's config editor) is `pinmap.py apply`'s
  output. `printer.cfg` itself is never changed, and the repo is mounted read-only.
- **What the container adds** in its top `printer.cfg`: each `[mcu]`'s `serial` (its simulator's pty, 250000 baud)
  and `restart_method: command`, and `homing_retract_dist: 0` for `stepper_x`, `stepper_y` and `stepper_z`. A simulated endstop reads its pull-up, so
  it is triggered from the start: without the retract, `G28` ends at once at `position_endstop`, as
  mainsail-crew/virtual-klipper-printer does. Each probe's pin (`[tools_calibrate]` here) is inverted there, so it
  reads untriggered (below).
- **The save file:** `madmax/offset_save_file.cfg` is copied to `~/printer_data/config/offset_save_file.cfg` at each
  start, as the batch tests seed it.
- **Nothing persists:** configs, logs, Moonraker's database and the save file live in the container and go when it
  stops. Edits made in Fluidd's config editor are lost; to keep one, make it in `cad/klipper/` and restart.
- **Same limits as batch mode, plus:** probes never trigger and the endstops read triggered. A board that klippy
  resets (`FIRMWARE_RESTART`, or the restart after a shutdown) is restarted by `reset_watch.py`: simulavr has no
  watchdog to reboot it.
- **Heaters heat:** each board runs `platform/virtualprinter/heatsim.py` (Kalico's `scripts/avrsim.py` plus a
  thermal model). For each heater whose sensor is a thermistor on the same board (here `extruder` and `extruder1`;
  the start log lists them), it follows the heater pin's PWM and drives the thermistor's ADC pin with the reading a
  first-order heater would give: ambient 25 °C, heating toward 25 + 350 °C at full power (a bed: 25 + 120), cooling
  back to 25 °C when off. So `M104`/`M109`, `SET_HEATER_TEMPERATURE` and Fluidd's heater fields heat to the target,
  hold it under Kalico's own PID, and cool when set to 0. The model runs in the board's simulated time (klippy's
  print time), so the PID sees a plant like a real one; but simulavr runs 10 to 25 times slower than real time, so
  on the wall clock heating is much slower than on a printer: on 2026-11-19 (a busy machine), `M104 T0 S200` reached
  197 °C after about 10 minutes, held 198 to 201 °C, and after `M104 T0 S0` fell to 152 °C in 5 minutes.
  verify_heater counts wall-clock time, so the container's top config stretches its checks on each simulated heater
  30 times (`[verify_heater extruder]` `check_gain_time: 600`, `max_error: 3600`); a heater that doesn't heat still
  shuts the printer down, only later. A first try with the model on the wall clock heated at real speed, but the PID
  (which runs in print time) lagged it and swung by ±10 °C. Not modelled: filament, part fans. A board restart
  starts its heaters again at 25 °C. The VT350 has no `[heater_bed]` yet, so `M140`/`M190` answer "Unknown command".
- **Probes:** a simulated input reads its pull-up, so `^PG11` (the Zero's NC switch: high when pressed) read
  triggered and `TC_GET_PROBE_POSITION` stopped at once with "Probe triggered prior to movement". The top config
  inverts it (`^!`), so the probe reads untriggered, as in batch mode, and each probing move runs its full distance
  (down to Z `position_min`). On hardware the switch is closed (low) until touched, so the real config needs no
  change. A probing move is a live move the board must keep pace with, and on a busy machine a simulated board can
  fall behind and shut down ("Timer too close", 2026-11-19, two virtual printers on one machine); `FIRMWARE_RESTART`
  clears it. The offset macros' plumbing is checked in batch mode instead (`TcOffsets`, below).
- **Slow boards:** simulavr runs far below real time: klippy measures each board at 1 to 1.5 of its 20 MHz, and
  says so at connect ("MCU 'mcu' configured for 20000000Hz but running at 2000000Hz!" or similar). That warning is
  expected; nothing to fix. On a busy machine a board can miss klippy's 5 s connect window and klippy stops with an
  error; `start` then restarts klippy, up to 3 times, and says so.
- **When `printer.cfg` gains a pin** (a `[heater_bed]`, a fan; #15), CI fails until the virtual printer covers it:
  `pinmap.py check` (the new pin isn't in `pinmap.json`: regenerate it with `pinmap.py generate`, which keeps the
  other pins where they are) and `prepare.py --check` (the same, plus every heater must be one the container
  simulates: heater and thermistor on the same board, and a `sensor_type` that is a thermistor in Kalico's list at
  the kalisim commit). A heater it can't simulate would read a steady 25 °C and shut the printer down on a target.
  `test_virtual_printer.py` adds a fake `[heater_bed]` to a copy of this folder and expects both to fail.
- **A reproducible build:** every input is pinned, and each pin is on [`cad/tools.md`](../tools.md) (CI fails when one
  isn't). Debian packages at exact versions from snapshot.debian.org as of `DEBIAN_SNAPSHOT` (a version Debian has
  since replaced still downloads); pip packages by version and sha256 (`--require-hashes`); simulavr by commit and by
  the sha256 of its tree, so another copy builds the same source or fails. If the pedrolamas mirror goes away, build
  from the owner's fork (it has the tags simulavr's version needs): `docker build --build-arg
  SIMULAVR_URL=https://github.com/dvystrcil/simulavr.git ...` (`virtualprinter.sh` builds with the default). The
  monthly health review checks that both still serve the pinned commit and tree
  (`platform/virtualprinter/check_sources.sh`), and watches the simulavr and Moonraker commits for upstream moves.
- **Moonraker's `docs` root** is Kalico's `docs/` at the image's commit (the published Kalico image has none, and
  Moonraker warned "Supplied path (/opt/klipper/docs) for (docs) is invalid").
- **What to click (AC2),** in Fluidd. `INITIALIZE_TOOLCHANGER` and `UNSELECT_TOOL` are klipper-toolchanger
  commands, not macros, so Fluidd has no button for them: type them in the console. `T0`, `T1` and the `TC_*` macros
  are under Macros (or typed).
  1. Home: the home button, or `G28`. The head ends in the homing corner, X 346 Y 340.19 Z 0.
  2. Move off the corner: `G0 X175 Y175 Z10 F6000` (or the jog buttons). Why: see "Probing in the corner" below.
  3. `INITIALIZE_TOOLCHANGER` (console): "toolchanger initialized, active None". Without it, `T0` answers "Cannot
     select tool, toolchanger status is uninitialized" (no tool detection yet, above). Any error during a tool
     change puts the toolchanger back to uninitialized (klipper-toolchanger does that on every command error), so
     after one, run it again.
  4. `T0`: "Picking up tool T0", then two "Unknown command: SET_INPUT_SHAPER" (expected: no `[input_shaper]` yet, as
     in batch mode), then "Selected tool 0 (tool T0)". A tool change takes one to a few minutes on simulavr, longer
     on a busy machine.
  5. `T1`, then `UNSELECT_TOOL` (console): "Dropping off tool T…", with "Unknown command:
     STOP_TOOL_PROBE_CRASH_DETECTION" (expected, as in batch mode), then "Tool unselected".
  6. The part-fan sliders (`part_fan_t0`, `part_fan_t1`); `SET_FAN_SPEED FAN=part_fan_t0 SPEED=0.5`.
  7. Heat: `M104 T0 S200` (or T0's extruder field in Fluidd). The temperature climbs, slowly (Heaters heat, above),
     and holds near 200 °C; `M104 T0 S0` lets it cool.
  8. `TC_*` macros: `TC_ADJUST_OFFSET` with no arguments answers "Tool must be specified" (expected). The probing
     ones (`TC_GET_PROBE_POSITION`, `TC_FIND_TOOL_OFFSETS`) run with T0 over the Zero on the printer; here they may
     stop the printer (Probes, above).

  **Probing in the corner:** on 2026-11-19, `G28`, then `TC_GET_PROBE_POSITION` in the corner, then `T0` failed
  with four "Move out of range: 346.000 340.190 1.000" and left the toolchanger uninitialized. A probing move (even
  one that stops at once) ends by setting the head's position from its stepper positions; for CoreXY that is
  y = ((x+y) − (x−y)) / 2, which gives Y 340.19000000000005, past `position_max` 340.19 by a rounding error. `T0`
  saves that position and its last leg moves back to it (`t_command_restore_axis: XYZ`), and Kalico refuses it.
  `T0` straight after `G28` works (exact position), and so does anything after a move off the corner. Not a macro
  bug: on the printer the probe runs over the Zero (Y −12.5), never at an axis limit, but any probing move that
  ends at exactly `position_max` would do the same.
- **What's pinned:** `platform/virtualprinter/Dockerfile` (simulavr, Moonraker, its Python packages, Fluidd).

### Keeping pins current

Two automations keep the pins above (and kalisim's) moving, with no AI and no hand edits; each opens a PR you merge
once its checks are green. Every step is `cad/klipper/repin.sh`, which runs the same by hand from the repo root.

- **Renovate** (`renovate.json`, on the shared `dvystrcil/renovate-config` preset, no automerge): one "virtual printer
  pins" PR on the 1st of each month for the builder image digest (`python:3.12-slim-bookworm@sha256:…`), simulavr's
  commit (`SIMULAVR_SHA`, pedrolamas/simulavr's `master`, a git-refs custom manager) and `setuptools`; and, as in every
  repo on the preset, the GitHub Actions (third-party ones pinned by SHA). Renovate can't compute simulavr's tree
  sha256, `pip_lock.py`'s hashes or `cad/tools.md`, so the **renovate-fixup** job in
  `.github/workflows/repin-virtualprinter.yml` does, on Renovate's branch (`repin.sh fixup <merge base>`), and
  commits them. Left out on purpose: Moonraker's packages (below), and the Kalico image, which moves with
  `KALICO_SHA` by hand (the health review reports the drift).
- **The monthly repin** (same workflow, the 2nd of each month, or Actions > "Repin the virtual printer" > Run):
  `repin.sh monthly` moves `DEBIAN_SNAPSHOT` to that day in both Dockerfiles, re-pins every apt package to the
  version the snapshot serves (`platform/kalisim/apt_repin.py`, in each stage's base image), re-resolves Moonraker's
  python packages within Moonraker's own ranges at `MOONRAKER_SHA` (a `pip freeze` in the kalisim image, then

## The image (`kalisim/Dockerfile`)

- **Runtime:** Kalico's published container, `ghcr.io/kalicocrew/kalico`, pinned by digest. Its `klippy/.version` is `v2026.11.00-30-g991e1823`.
- **Dictionaries:** the published image ships klippy only, so a first stage builds the firmware from Kalico's source at `KALICO_SHA` = `991e1823e983a31d26b9264d2b6305fd64e3a09a`, one build per `kconfig/*.config`:
  - `octopus-pro-h723`: STM32H723, 128 KiB bootloader, 25 MHz crystal, USB PA11/PA12 (Kalico's Octopus Pro v1.1 sample config).
  - `o2s-left`, `o2s-right`: STM32F072, no bootloader, 12 MHz crystal, USB PA11/PA12 (O2S User Manual v1.5 §4). USB serials are `Orbitool_O2S_L` and `Orbitool_O2S_R`. Upstream gives every board `Orbitool_O2S`, so two boards would collide in `/dev/serial/by-id`.
- **klipper-toolchanger:** the first stage fetches `viesturz/klipper-toolchanger` at `TOOLCHANGER_SHA` = `94756dfde9b729fd69f9b8780067821c5c99a528` into `/opt/toolchanger`. The runtime stage copies four of its modules into `klippy/extras/`, and fails if Kalico already has a file of that name. They go in `extras/`, not `plugins/`, because they import Kalico's `probe` relatively (`from . import probe`), which only resolves there.
- **Checks:** `build_dicts.sh` fails if Kconfig dropped any requested setting. `test_kalico_batch.py` checks that both stages are the same commit, that the installed toolchanger modules are the pinned ones, and that Kalico's own `tools_calibrate.py` is kept.
- **Flashing the real boards:** the same `kconfig/*.config` files are the `make menuconfig` answers. Batch mode can't see USB names, so check `ls /dev/serial/by-id/` once both toolboards are plugged in.

## Nozzle offsets (#186 AC2)

Each head's XY and Z offset is measured on the **Mellow MultiHead Zero** (placed in lite-61: on the bed's front 2020, ball at printer X 175, Y −12.5, its top about Z 10). The macros are MadMax's `tc_offset_calibration_macros.cfg` (written for Nudge): `TC_GET_PROBE_POSITION` with T0 over the Zero, then `TC_FIND_TOOL_OFFSETS TOOL=1`. The results go to `~/printer_data/config/offset_save_file.cfg` (`[save_variables]`).

- **The NC switch needs no inversion.** klipper-toolchanger's `tools_calibrate.md`: "normally closed: nudge (no inversion)". `tc_offsets.cfg` uses `^PG11` (pull-up; the Octopus Pro's DIAG3). It goes to an Octopus endstop input (owner, 2026-11-17): DIAG3, the first one free (X, Y, Z use `PG6`, `PG9`, `PG10`). The cable route from the bed is still open (#186).
- **MadMax's copies don't run on Kalico.** They read `printer.tools_calibrate.last_x_result`, `last_y_result` and `last_z_result`, which klipper-toolchanger's module reports. Kalico's own `tools_calibrate`, which the build keeps (#116, option A), reports `last_result` (an x, y, z tuple) instead. Kalico's Jinja raises `UndefinedError` on the missing field, so the macro stops and nothing is saved. `tc_offsets.cfg` replaces `_TC_SHOW_LAST_RESULT`, `_TC_SAVE_PROBE_POSITION` and `_TC_UPDATE_OFFSETS` with copies that read `last_result.x/.y/.z`.
- **A failed offset run can't save the probe position as an offset.** After `TOOL_LOCATE_SENSOR`, Kalico's `last_result` is the sensor's position. It becomes an offset only when `TOOL_CALIBRATE_TOOL_OFFSET` succeeds. `_TC_UPDATE_OFFSETS` refuses to save while the two are equal.
- `test_kalico_batch.py` (`TcOffsets`) runs the sequence in batch mode and checks that the saved position and the T1 offset equal what Kalico logged. It also checks that MadMax's own copies fail. Batch mode has no probe to touch: each probing move runs its full 100 mm, so the test lowers Z `position_min` and loosens `samples_tolerance` in a wrapper config. The values it measures mean nothing; only the plumbing is checked.
- **The saved offsets are applied on every tool change.** `toolchanger.cfg` defines `T0` and `T1` as MadMax's `toolboard_<n>.cfg` does: each calls `_CHANGE_TOOL` (`toolchanger_macros.cfg`), which clears the old tool's offsets (keeping any Z tweak made since), selects the new tool, applies its saved `t<n>_offset_x/y/z` with `SET_GCODE_OFFSET`, and moves the part-fan speed to it. The macros must come **before** the `[tool]` sections: klipper-toolchanger registers its own `T<n>` as each `[tool]` loads, unless one already exists ("gcode command T0 already registered" otherwise). They also need MadMax's `variable_color`, which its macros set.
- **Copy the save file before the first tool change.** `_CHANGE_TOOL` reads every tool's offsets from `~/printer_data/config/offset_save_file.cfg`; start it as a copy of `madmax/offset_save_file.cfg`. Without it, `_CHECK_SAVED_OFFSETS` stops the tool change and names the missing variables (rather than `_CHANGE_TOOL` failing part-way on a Jinja error).
- **Part fans:** `printer.cfg` has `[fan_generic part_fan_t0]`/`part_fan_t1`, which `_CHANGE_TOOL` and MadMax's `M106`/`M107` drive, on the O2S's 2/3-wire fan pins (`!PA10`, enable `PB14`). **PLACEHOLDER** until the part fans are chosen; a 4-wire fan uses `PB0`.
- `TcOffsets` also checks: the measured T1 offset is the G-code offset after `T1`; each tool gets its own saved offset and a Z tweak carries over; the part fan follows the tool; a save file without the offsets stops the change. In batch mode a fan change takes effect only once a move follows it (Kalico's fan requests are flushed by the move queue; a dwell isn't enough), so the fan test moves before each read. **A fan set just before a tool change reaches the new tool:** `_CHANGE_TOOL` reads the fan's speed when it starts, and Kalico reports a fan's speed only once its request is applied (when the queued moves flush), so without a flush it read the old speed and the new tool's fan started off. Each `T<n>` starts with `M400`; the test sets the fan, moves, then changes tool.

`kalisim` runs klippy with a sandbox `HOME` that has an empty `printer_data/config/`, so the `[save_variables]` file is created there and not in your own home folder. `home_files` (`--home-file REL=SRC` on the command line) copies a file in first: the tests seed the save file that way.
